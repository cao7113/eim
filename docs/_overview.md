# Eim 产品概览

> 状态：产品方向与整体架构概览。用于指导需求讨论和产品取舍；具体功能以各专题方案及实际验证为准。

## 产品定位

Eim 是面向英语持续学习者的个人学习中心，帮助用户把日常遇到、值得学习的内容顺手收集起来，以轻松、可持续的方式理解、记忆和运用，并看见自己的成长。

**简单、方便、好玩、成长**是核心设计原则：

- **简单**：聚焦清晰、必要的学习动作，降低开始学习的门槛。
- **方便**：让查词、收录、记录上下文和回顾自然融入阅读与日常工作。
- **好玩**：用轻量、有反馈的互动提升自愿参与，而不把积分、打卡或游戏任务变成目的。
- **成长**：帮助用户形成个人积累，并逐渐提升回忆、理解和实际运用能力。

产品价值在于**增强人本身**，而不是与词典或 AI 比词条数量、来源广度或回答深度。词典和 AI 是服务学习的能力，不是产品定位本身。

## 产品主张与差异化假设

可用于检验产品方向的一句话：

> **遇到好词，顺手收进来；用轻松的方式学会它，看见自己的进步。**

[沉浸式翻译](https://immersivetranslate.com)主要帮助用户理解正在阅读的外语内容；Eim 希望承接“理解之后”的个人学习过程：低成本收集有价值的词和语境，找得回来、学得进去，并逐渐转化为自己的能力。两者可以互补，而非在翻译覆盖面、词典规模或 AI 能力上正面竞争。

这是一项待验证的产品假设，不代表差异化或用户需求已被证明。产品探索应持续回答：

- **目标用户与时刻**：谁最常遇到“当下看懂了，之后却记不住或找不回来”的问题？优先选择一个高频、具体的阅读或工作场景。
- **自然入口**：如何让用户在遇到值得学习的内容时用最少步骤收录，并在有帮助时保留来源与上下文？
- **持续使用**：什么样的短时回顾或轻量练习，让用户愿意主动回来，而非增加课程、计划或打卡负担？
- **成长证据**：如何从收藏之外观察用户是否更容易回忆、理解或运用？反馈要帮助用户，而非制造数字压力。
- **趣味边界**：哪些互动能帮助学习持续发生？避免为了“好玩”堆叠与学习结果无关的游戏机制。
- **暂缓事项**：不能明确改善学习体验的多词典、多模型或复杂 AI 能力，先不建设。

## 核心学习闭环

以一个简单可持续的个人学习闭环组织功能：

1. **遇见与理解**：用户在阅读或工作中遇到词汇；通过浏览器扩展等入口快速查词，不打断当前任务。
2. **收集与关联**：用户主动收藏，形成个人生词本；在明确授权和可控的前提下，保留来源、上下文与个人笔记。
3. **回顾与练习**：用户能快速找回个人积累，通过轻量、有反馈的回顾逐步加深记忆。
4. **运用与成长**：让用户把学过的内容用于真实理解或表达，并以有意义的方式看到长期进步。

当前优先把“遇见—收集—找回”做得可靠顺手，再依据真实使用逐步验证回顾、练习和成长反馈。不要因为规划了完整闭环，就一次性实现所有学习模块。

## 产品与技术架构

### 当前产品分层

- **日常入口**：浏览器扩展提供划词查词和显式收藏，尽量不打断用户正在进行的阅读。
- **个人学习中心**：Web 端承载个人生词本、来源上下文、笔记、检索与后续复习；用户数据与公共词典数据分离。
- **基础查词能力**：当前以 ECDICT 提供可用、低延迟的词典结果；查词核心路径不依赖 LLM。
- **服务端与管理**：Phoenix 应用提供账号、个人数据、API 和管理能力；扩展作为独立客户端与服务端协作。

### 演进边界

- **词典/词库**：当前只接入 ECDICT。将来可以接入其他词典或词表，但要在真实需求、许可与使用场景明确后再扩展。
- **AI 能力**：将来可为语境解释、翻译或搜索提供 AI 辅助；它应是可控的增强层，不能让基础查词和个人学习中心因模型不可用而失效。
- **多 Provider 与智能路由**：属于架构预留，不是当前功能承诺。只在用户价值、隐私、质量、成本和维护收益明确后引入。
- **统一原则**：词典提供可追溯的来源内容，AI 提供生成能力，个人生词本保存用户自己的学习资料；这些数据和职责不能混为一体。

## 产品取舍原则

评估需求、设计和架构时，依次检查：

1. 是否解决目标用户真实、反复出现的学习问题？
2. 是否让学习更简单、方便、有趣，并促进可感知的成长？
3. 是否能以足够小的步骤验证价值，而不是先构建复杂平台？
4. 是否尊重用户控制、隐私、来源许可和个人数据边界？
5. 如果移除该功能或技术扩展，核心学习体验是否会明显变差？

若价值尚不明确，优先保持简单并验证假设，不以“未来可能需要”作为提前建设的充分理由。

## 项目设计笔记与技术框架

本节迁移自仓库根目录的 `NOTE.md`，保留早期设计想法、技术选型和参考链接。候选功能不代表已承诺的路线；具体状态以代码和专题方案为准。

### 初期功能范围

- **浏览器扩展**：划词查词/翻译，并由用户主动收藏。
- **Web 学习中心**：管理个人生词本，后续可提供 LLM 辅助学习能力。
- **管理能力**：缓存及服务运行状态管理。

扩展是日常学习入口，Web 是个人积累与回顾中心。收藏、上下文和学习进度属于个人数据；词典内容和 AI 生成内容保持来源清晰、职责分离。

### 候选方向池

以下是早期收集的探索方向，尚未按用户需求验证或确定优先级：

- 英汉与汉英互译、LLM 辅助。
- 朋友间的词汇分享或词汇对对碰。
- 行业术语与行业知识。
- 易错词整理。
- Global news 等阅读材料。
- 四六级、考研及专业词汇学习。
- 演讲、快速阅读、听说读写训练。
- 原版名著阅读

候选方向应先回到核心原则评估：它是否让个人学习更简单、方便、有趣并促进成长？是否能从小范围真实使用中验证？不因列表中的想法直接扩张产品范围。

### 整体架构与技术选型

- **主应用**：Phoenix；Web 界面主要使用 Phoenix LiveView，服务端承载账号、学习中心、API 和管理功能。
- **浏览器扩展**：位于 `extension/`，采用 WXT（基于 Vite）和 Svelte，并使用 Bun 工具链。早期 UI 方案曾考虑 Svelte、Solid、Preact；当前已采用 Svelte。扩展与后端分开组织，未来可按实际需要独立维护或开源。
- **后端领域与 API**：使用 Phoenix 1.8+ 和 Ash 3.0+ 是早期记录的目标基线；当前具体版本以项目依赖为准。优先采用 AshJsonApi 风格，并提供 OpenAPI/Swagger UI 能力。
- **基础设施与集成**：PostgreSQL、AshAuthentication、Oban；HTTP 请求使用 Req。早期笔记也提到 ReqClient，当前项目规范优先使用 Req；类型共享等方案（例如 AshTypescript）仍需按实际需要评估。
- **扩展交互方向**：早期提出“Learn with quick Vim habit”，可理解为探索快速、键盘友好的学习操作；它是交互灵感，不是要求用户学习 Vim 的前置条件。

技术选型服务于易用和可持续交付：扩展负责低打断的查词与收录，Phoenix 应用负责可靠保存和呈现个人学习资料。除非规模、团队或部署需求发生变化，不为拆分服务或独立部署而提前增加复杂度。

### 查词数据与 AI 的演进设想

当前以 ECDICT 支持基础查词。早期采用“先词典、后 AI”的思路：低延迟、可用的词典结果先支撑划词到收藏的学习入口；AI 是可选增强，而非基础查词的依赖。AI 服务不可用、超限或未配置时，基础词典查词仍应可用。

以下是早期记录的潜在数据源和用途，均须在接入前验证实际价值、数据质量、许可、署名要求和维护成本：

- **[ECDICT](https://github.com/skywind3000/ECDICT)（当前已接入）**：中文释义、词形及现有数据中的难度/词频相关信息。
- **Kaikki / Wiktionary 子集**：可评估导入高频词的英文释义和例句。
- **Tatoeba**：可评估为常用词补充中英例句。
- **OEWN**：可评估作为词义关系或语境解释的候选参考数据；不得将其描述为未经验证的 LLM 专属来源。
- **Microsoft 术语**：可评估作为技术释义数据，在相关阅读场景中提供补充；需先确认数据许可和可用性。
- **LLM**：可在词典信息不足或用户明确需要语境解释时提供生成式辅助，并清楚标记生成内容及其依据。
- **[Rememberry](https://www.rememberry.in/)**：早期参考产品；当时记录其词典来源为 [FreeDictionaryAPI.com](https://freedictionaryapi.com/) 与 [Wiktionary](https://www.wiktionary.org/)，现状及授权需重新核验。

接入任何来源都应保留来源名称、版本或日期，以及授权和署名信息。不同来源不可未经许可审查就混合分发；AI 生成内容也不能伪装成来源词典事实。多词库和多 LLM Provider 的详细边界见[词典浏览与多词库架构参考](./词典浏览与多词库架构参考.md)。
