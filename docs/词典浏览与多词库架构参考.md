# 词典浏览与多词库架构参考

> 状态：需求与技术方案参考，供后续拆分实施任务；不是当前实现承诺。  
>
> 当前基线：ECDICT 是唯一已接入的词典数据源。
>
> 整体产品定位、设计原则和能力分层见[产品概览](./_overview.md)。

## 1. 背景与目标

当前系统以 ECDICT 提供英文词条、词形和划词查询。下一阶段可增加面向用户的词典浏览体验，让用户查看词典数据覆盖范围、搜索词条并阅读完整详情；之后可扩展难度分级和随机练习。

### 产品方向约束

本方案讨论多词典、多词库及多 LLM Provider 的未来技术边界，不代表当前要建设完整的词典平台或 AI 平台。功能优先级应服从[产品概览](./_overview.md)中的定位和取舍原则：简单、方便、好玩、成长；只有能改善个人学习体验的扩展才进入实施范围。

架构和页面从一开始就应容纳多个词典数据源。将来用户可能依据订阅权益选择一个词典、自动选择合适来源，或合并展示多个来源的结果。因此：

- 不把 ECDICT 的字段和规则当作所有词典的通用模型。
- 不把“同一个词”误认为“只有一条词典释义”；不同来源可以有不同解释、音标、例句和授权条件。
- 不把词典 Provider 与 LLM Provider 混为一层：词典提供可追溯的词条数据，LLM 提供基于任务的生成、解释或搜索辅助。
- 不把订阅权益、词典可用性和词条数据揉进单一查询函数或页面组件。
- 当前阶段避免为尚不存在的来源建造复杂平台；先建立清晰边界，并保持 ECDICT 可运行。

## 2. 术语约定

本文中的术语按以下定义使用，避免把内容来源、词汇集合、用户数据和模型服务统称为“词库”或“来源”：

| 术语 | 本文定义 | 典型内容 / 作用 | 不等同于 |
| --- | --- | --- | --- |
| **词典** | 面向查词的参考内容产品或资源；产品/UI 层优先使用此词 | ECDICT、双语词典、专业术语词典；提供释义、音标、词性、例句等 | 词表、用户生词本、LLM |
| **词库** | 后端维护和版本化的内容数据集/存储单元；偏数据和工程术语 | 一个可导入、授权、启停、统计的 dictionary corpus；可承载一个词典或结构不同的来源数据 | 用户筛选的词表、用户个人收藏集合 |
| **词典数据源 / 来源** | 具体提供词条数据的来源实例及其版本、许可和来源标识 | ECDICT 某个导入版本、授权的第三方词典 API | AI Provider；来源信息是数据溯源，不是模型选择 |
| **词表** | 有明确收录规则、版本和范围的词汇集合，通常只规定“哪些词属于集合”及可选标签/等级 | CET-4、主题词表、产品精选词单、CEFR 对照词表 | 提供完整释义的词典；用户个人生词本 |
| **个人生词本** | 用户拥有的学习集合及其个人状态；当前项目中的收藏、笔记和后续掌握度 | 用户收藏的词目/词条引用、笔记、采集上下文、练习记录 | 公共词库、词典数据源、可共享的官方词表 |
| **LLM Provider / AI Provider** | 提供生成式模型能力的服务商或适配器 | 模型推理、翻译、解释、query rewrite；有独立的能力、费用、隐私和可用性 | 词典或词条来源 |
| **AI sourcing** | 本文不把它当作未定义的架构组件名。若讨论“选择哪家模型/服务”，统一称 **AI Provider 选择与路由**；若讨论给 AI 提供可引用资料，称 **检索增强（RAG）与证据溯源** | Router 根据任务/权益选择模型；RAG 检索有权限的词典、词表或用户内容，并将引用与生成结果关联 | 词典来源选择、抓取/采购词库，或 LLM Provider 本身 |

### 使用规则

- 面向用户的导航、页面标题和操作使用“词典”；说明后端数据集、导入、版本和统计时使用“词库”。
- “词表”只表示成员资格/筛选集合。若词表包含外部等级，应记录发布方和版本；不能把它的等级自动当成词典定义或个人掌握度。
- “个人生词本”是用户数据域，收藏一个词条不等于复制或拥有原词典内容；可关联词典词目，也可关联具体来源词条，并附加个人 note、采集记录和学习状态。
- “来源”必须带类型：词典数据源、词表来源、用户采集来源或 AI Provider。避免单独使用“AI 来源”来指代模型供应商。
- AI 生成内容应与被引用的证据分离：AI Provider 是生成者，词典/词表/用户授权内容是可引用的数据来源；RAG 引用不代表模型输出本身已被来源证实。

## 3. 产品范围建议

### 第一阶段：词典浏览

#### 覆盖概览

- 展示当前可用词典及其名称、语言、数据源版本、导入时间和条目数量。
- 展示各词典数据集的字段完整度，例如音标、释义、词性、标签、词频和词形数据覆盖情况。
- 统计维度以“词典数据集”为单位，避免将不同来源的记录相加后误称为独立词汇量。
- 后续可展示各来源间的词条重合量，但需要明确定义规范化规则和统计口径。

#### 搜索与列表

- 支持按单词/词形搜索，按词典、语言、词性、主题词表、词频分段等筛选。
- 展示词条主词形、简短释义、音标、来源标识和可用词典数量。
- 使用服务端分页；筛选和排序条件写入 URL，便于刷新、分享和浏览器导航。
- 明确区分公共词典浏览与个人生词本：前者是按许可提供的只读数据，后者是当前用户的收藏、笔记和学习状态。
- 避免在数十万条数据上使用无索引的任意子串搜索或随机排序；搜索能力以有索引的词形/规范键查询为主。

#### 词条详情

- 展示规范词形、查询到的词形、词性、音标、释义、例句、标签及相关词形。
- 每个释义/字段标明来源；不同词库内容分区展示，不静默拼接成一个看似统一的答案。
- 支持从详情收藏到个人学习中心；个人 note 和练习记录不回写到公共词典数据。
- 来源字段缺失时隐藏对应字段，不用空值占位影响阅读。

### 后续阶段：难度与随机练习

- 从小而闭环的题型开始，例如“单词选择释义”，再考虑拼写、听辨、例句填空等。
- 用户可选择词库、难度区间、词性或主题范围；系统只从其可访问的词库中出题。
- 初期难度应标记为“估算”，可参考词频分段、词库标签或经验证的等级映射；不能将 ECDICT 词频直接包装为权威 CEFR、考试或年级等级。
- 练习、答题历史和个人掌握状态属于用户数据，应独立存储，不修改共享词条。
- 题目应记录使用的来源和数据版本，以便来源更新后仍可解释历史题目。

## 4. 领域概念与数据边界

建议逐步区分以下概念：

1. **词目（Headword / Lexical concept）**：跨来源关联用的规范词形或概念。初期可以只做规范化 key，不要求解决完整的词义消歧。
2. **词典数据集 / 词库（Dictionary corpus）**：可独立启用、授权、导入、版本化和统计的内容集合，例如 ECDICT 数据集或未来的专业词典数据集。
3. **来源词条（Source entry）**：某个词典数据集中的原始词条及其原始字段。它应保留来源特定字段、来源 ID 和版本。
4. **查询结果（Lookup result）**：针对用户查询、词典数据源选择及权限策略生成的应用级响应。它可以包含一个或多个来源词条，并保留匹配方式和来源信息。
5. **词表（Word list）**：用于筛选、分类、教学或难度对照的词汇成员集合；可引用词目/来源词条，但不代替其释义数据。
6. **个人生词本（Personal vocabulary）**：用户的收藏及其笔记、上下文、练习历史和掌握状态；它引用公共词目/来源词条，不属于公共词库。
7. **AI Provider**：执行生成式任务的外部模型服务，具有独立的能力、版本、延迟、费用、数据处理条件和可用区域；它不是词典来源，也不应伪装成词典词条。
8. **AI sourcing**：须按语境拆成 Provider 选择与路由，或 RAG 检索及证据溯源；不要用此词泛指词典来源和模型供应商的混合物。

跨词典数据源去重并非简单的 `lowercase(word)`：同形异义词、词性差异、变体和短语都可能需要独立处理。因此第一版只采用 NFKC、空白与大小写规范化作为**搜索/关联键**，不据此合并或丢弃来源原始记录。

## 5. 当前实现基线与演进建议

当前代码中的主要边界：

- `Eim.Dict.Lexeme` 保存 ECDICT 来源词条和字段，包括 `word_lc`、`sw`、释义、词性、标签、Collins、Oxford、BNC/FRQ 排名、lemma、source 和 source version。
- `Eim.Dict.LexemeForm` 保存词形与其对应词条。
- `Eim.Dict.Lookup` 执行精确匹配、词形匹配和模糊匹配，并产出 `Eim.Dict.Entry`。
- `Eim.Dict.Importer` 负责 ECDICT CSV 的导入和词形重建。
- `Eim.Dict.Import` 记录来源版本、文件哈希和行数。

建议采用渐进迁移：

### 近期：先抽象查询边界，不迁移全部数据

- 将 ECDICT 查询实现包在来源适配器/Provider 模块后面，例如 `Eim.Dict.Providers.Ecdict`；Provider 负责该来源的搜索、详情映射和来源元数据。
- 由统一的 Dictionary 服务根据显式策略选择 Provider，输出稳定的查询结果结构。
- 统一结构保留来源 ID、来源名称、词库版本、匹配类型及来源特定字段；对外 API 增加字段时采用向后兼容方式。
- 继续使用现有 ECDICT 表和导入器，不为了抽象而立刻搬迁 77 万条记录。
- 明确 `lookup` 现有的 ECDICT 返回行为为默认策略，新增来源不得意外改变它。

### 增加第二个来源时：决定是否引入注册表和统一索引

当第二个词库真正接入后，再依据数据形态决定：

- 若各来源数据结构差异大、授权不同、需要保留来源原始字段：使用独立 source-entry 表/资源，或按来源隔离的存储；通过应用层适配为统一结果。
- 若搜索性能需要跨来源统一检索：增加轻量规范词目/搜索索引，关联一个或多个 source entry；索引只服务查找和聚合，不替代来源原文。
- 若来源字段高度兼容且授权允许合并存储，才考虑共享表加 `dictionary_id`。不要默认所有未来来源都适合一张巨型宽表。
- 词形也应有来源与语言归属；只有确认同一形态规则和关联语义时才能跨来源复用。
- 词典适配器与 LLM 适配器使用不同协议、注册表和结果类型；两者只在上层应用编排中组合。

无论采用何种存储，都需要词库注册信息：稳定 ID、显示名、语言、描述、版本、来源、许可/归属说明、导入状态、启停状态和支持能力。来源许可应在接入前核实，并影响可缓存、可展示、可导出和付费访问范围。

## 6. 查询、选择与付费策略

将“可用哪些来源”和“如何组合结果”作为两个独立决策：

- **访问策略**：用户、订阅计划和地区是否有权使用某词库或某字段。
- **查询策略**：单来源优先、按顺序 fallback、并行多来源聚合，或用户手动指定来源。

建议用显式策略对象/配置描述，而不是在 Provider 中直接读取订阅系统：

```text
LookupRequest
  query
  language
  source_selection: default | one(source_id) | multiple(source_ids)
  result_mode: preferred | fallback | aggregate
  user_entitlements

LookupResult
  normalized_query
  match_type
  entries[]:
    source_id
    source_name
    source_version
    source_entry_id
    canonical_term
    source_payload
    normalized_fields
```

建议的策略语义：

- **default/preferred**：根据产品默认配置选择一个来源，适合作为当前单结果查词 API 的延续。
- **fallback**：先查首选来源，未命中或字段不足时再查询候选来源；响应应标明最终命中来源。
- **aggregate**：并行查询用户有权访问的来源，按来源分组返回多个结果；不要把不同来源释义拼成无出处的单个字符串。
- **explicit selection**：用户选择词库/词典后仅查询指定来源；无访问权时返回明确的升级或权限状态，不泄露受限词条内容。

性能与可靠性要求：

- 每个 Provider 设定超时和错误分类；聚合模式允许部分来源失败，但必须带回来源级状态，不能将部分失败伪装成完整结果。
- 为用户权限和来源选择生成可审计的决策结果；不要让缓存键跨越订阅权益边界。
- 做缓存时至少考虑规范查询、语言、来源集合、策略版本、用户可见权限及来源版本。
- 来源排序、默认值和付费解锁逻辑集中在策略层；UI 只负责传递选择和展示服务端返回的可用选项。
- 付费权益变更不能要求改写词库数据；权限校验发生在查询入口及必要的数据访问边界。

### 多层查词与搜索服务

产品可以提供多个层次的查词与搜索，但建议由明确的服务能力组成，而不是把所有行为塞进一个不可预测的“智能查词”接口：

1. **词形规范化**：校验输入长度、语言和类型，统一空白/大小写等，不调用外部服务。
2. **精确词典查询**：使用索引查找词条，作为低延迟、可复现的首选。
3. **词形查询**：通过来源词库的 inflection/form 关系找到原型，并保留匹配过程。
4. **容错查询**：拼写近似、去标点等候选召回；返回候选和匹配类型，不将近似命中伪装为精确结果。
5. **多词库查询**：按用户所选来源及访问权益执行 preferred、fallback 或 aggregate 策略，结果按来源分组。
6. **语境解释/翻译**：可选调用 LLM，结合用户明确提供的上下文和已获许可的词典候选解释词义、区别近义词或翻译短语/句子。
7. **语义搜索**：后续可用 embedding 检索词条、例句或学习内容；LLM 可辅助 query rewrite/rerank，但最终结果仍应能回溯到真实记录。

分层不意味着每次请求都要顺序调用全部能力。服务端应根据任务、用户选择、权限、延迟预算和成本预算决定执行路径；普通单词精确命中不应无条件调用 LLM。用户应能区分“词典查词”“多词库比较”和“AI 语境解释”等模式。

建议将能力拆为可独立调用的应用服务，例如 `DictionarySearch`（词目/来源词条检索）、`Lookup`（对单个查询词解析词形并组合词典候选）、`ContextualExplanation`（基于候选和用户上下文生成解释）、`SemanticSearch`（检索相关词条/例句）。服务可以复用 Provider，但各自有明确输入、权限、响应和资源限制。

### 多 LLM Provider 架构

当前 ECDICT 方案已为 `Eim.Translation` 编排层和 `Eim.AI` Provider 抽象预留位置（详见 [ECDICT 词典方案的 LLM 预留清单](./ECDICT词典.md#9-llm-预留清单)）。后续建议扩展为多个可配置 Provider，而不是让业务代码直接依赖某个模型 SDK：

```text
ContextualExplanation / Translation / SemanticSearch
                 │ task request + policy
                 ▼
             Eim.AI.Router
       ┌─────────┼──────────┐
       ▼         ▼          ▼
   Provider A  Provider B  Provider C
       └─────────┼──────────┘
                 ▼
       normalized AI result
```

职责边界：

- **任务编排层 (`Eim.Translation` 等)**：决定何时需要 AI，准备最少必要的词典候选/上下文，构造有版本的任务请求，校验结构化输出。
- **AI Router (`Eim.AI`)**：依据显式策略选择一个或多个符合条件的 Provider，执行超时、并发限制、重试/故障切换和结果归一化。
- **Provider adapter**：封装各家 API 请求/响应、模型能力映射、错误分类和用量元数据；不得持有业务权限决策。
- **Dictionary Provider**：只负责词库查询和来源结果，不调用 LLM，也不依赖 AI 服务。

建议的任务请求/响应概念：

```text
AITaskRequest
  task: explain_word | translate_phrase | translate_sentence | rewrite_search
  query
  language_pair
  context?                 # 用户明确授权提供的最小上下文
  dictionary_candidates[]  # 可选、仅传许可允许且用户有权访问的数据
  output_schema_version
  policy: provider_policy, privacy_level, latency_budget, cost_budget

AITaskResult
  content
  task
  provider_id
  model_id
  prompt_version
  dictionary_references[]  # 可追溯的词典来源；AI 本身不列作词典来源
  usage
  cache_status
  warnings[]
```

Provider 选择建议：

- 支持显式指定 provider、产品默认 provider、按任务能力路由、按权益过滤后的候选列表。
- `primary/fallback` 适用于主 Provider 临时不可用；`compare` 或并行多个 Provider 应作为明确的用户/产品功能，因为成本和延迟会增加。
- 故障切换仅针对可重试的瞬时故障；认证失败、配额耗尽、内容策略拒绝和参数错误应有明确分类，不能无限重试或静默降级。
- 可按任务配置质量、延迟、成本、数据驻留和可用性策略；订阅权益只决定允许使用的能力/额度，不直接写入 Provider 实现。
- Provider/model/prompt 版本都应可追溯，以支持结果解释、缓存失效和评测对比。

安全、隐私与成本边界：

- API key 只存服务端 secret 管理设施，不进入浏览器、扩展包、日志或客户端配置。
- 请求前执行身份认证、权限检查、速率限制和额度控制；限制输入长度、并发、输出 token 和单次花费。
- 网页选区或学习笔记等私人上下文不得默认发送给第三方模型；仅在用户触发 AI 功能并获知数据用途后发送最小必要内容。
- 明确各 Provider 的保留/训练/区域策略；不得把不允许外传的词库授权内容放进 prompt。
- 日志记录 task/provider/model/prompt 版本、耗时、状态和用量等操作元数据；默认不记录原始 prompt、全文上下文或模型完整输出。
- 缓存键至少包含规范输入、任务、输出 schema、词典候选版本、provider/model、prompt 版本和隐私/权限范围；不得跨用户权益边界复用受限结果。
- 有来源依据的事实与模型推断分开呈现；AI 解释应标记为生成内容，不能把模型输出混入或覆盖原始词典条目。

## 7. 页面信息架构建议

建议将页面分为“词典目录/概览”和“词条浏览/详情”，避免混在单一列表页面：

### 词典目录与覆盖概览

- 顶部：页面说明和当前可用范围；按用户权限呈现可用词典。
- 主要内容：每个词典及其词库数据集的名称、语言、版本、条目数、字段覆盖率和更新时间。
- 支持按语言/主题筛选词典；付费词典显示能力与权益说明，不直接暴露无权访问的数据。
- 覆盖率明确计算口径，例如“有音标的词条 / 此词库数据集的全部词条”；支持字段按数据源变化，不要求每个词库都有同一组字段。

### 词条浏览与详情

- 搜索与筛选区域：搜索词、词典数据源选择、词性/词表标签/词频范围；来源控件需区分“只查某数据源”和“组合多个数据源”。
- 若提供多层查词，使用明确模式入口（如“词典优先 / 多词库 / AI 语境解释”），不要把模式、来源、排序、难度混成同一种 Tabs。
- 结果区：词形、摘要、来源徽标、匹配类型；结果按词目去重时，仍显示其下有几个来源版本。
- 详情区：按来源分区显示数据和版本，提供收藏到个人学习中心的动作。
- 当选择多个来源时，优先使用“一个词目、多个来源分区”的布局；窄屏可改为来源 Tab 或折叠分区。
- AI 内容应置于独立的“AI 解释/翻译”区域，显示生成标识及其引用的词典来源；不能与来源词条混为一个无出处释义列表。
- 词典设置和订阅入口可扩展为独立区域；不要把“词典数据源选择”“排序方式”“词表/难度”等不同维度全塞入同一组 Tabs。

页面文案应让用户理解：展示的是“词库中的来源条目”，不是系统保证唯一、权威的词义。来源和许可要求优先于视觉上的统一性。

## 8. 难度模型与练习数据

不要直接给 `Lexeme` 增加一个含义不清的 `difficulty` 整数，并将它当作固定真值。建议后续引入版本化的难度评估：

- `difficulty_scheme`：方案名称与版本，例如产品内部估算、CEFR 对齐或考试词表对齐。
- `difficulty_value` / `difficulty_band`：数值或分档。
- `basis`：依据的排名、词表或人工审核规则。
- `confidence` 与更新时间：区分强证据和粗略估算。
- 难度可绑定词目或来源词条，避免把某来源的频率排名误认为跨来源事实。

练习数据可在需求稳定后新增独立模型，例如 PracticeSession、QuestionAttempt 或 UserLexemeProgress。需要先定义匿名/登录使用、去重抽题、题目版本、正确率窗口和掌握度衰减，避免 MVP 直接引入复杂复习算法。

## 9. API 边界建议

- 公开只读浏览 API（若需要）与当前插件查词 API 可共享应用层查询服务，但应保持不同响应契约和速率/权限规则。
- 浏览 API 应支持分页、来源筛选、受控排序和详细字段投影；不要暴露数据库内部字段或整个未经筛选的原始记录。
- 查询响应明确包含 `source_id`、`source_name`、`source_version`、`match_type` 和来源条目标识。
- 多来源聚合返回列表及每个来源结果，不破坏当前单来源客户端的字段结构；可以通过版本化路由或新增聚合端点演进。
- 词库概览指标由导入流程维护或定期计算，页面请求不应在每次加载时全表扫描。
- 词库搜索、详情读取和练习取题都要执行相同的用户权益/许可校验原则。
- AI 能力使用独立任务 API/应用服务；请求中显式指定任务、来源选择策略和上下文授权，不允许客户端指定任意 Provider URL 或模型凭据。
- AI API 响应应区分 AI 生成字段与词典来源数据，返回 provider/model/prompt 版本、词典引用、用量和部分失败状态；敏感原文默认不回显到日志。
- 搜索 API 的精确/词形/模糊/多词库检索与 AI 语义辅助保持独立可观测，避免一次搜索隐式产生不可控外部模型调用。

## 10. 逐步实施路线

1. **需求定界与数据盘点**：确认浏览对象、搜索范围、覆盖指标口径、是否公开访问；盘点现有索引和 ECDICT 许可。
2. **单来源浏览 MVP**：只读词典目录、ECDICT 搜索/筛选/分页、词条详情、来源信息和收藏入口；不做付费、多来源聚合或游戏。
3. **稳定查询边界**：将 ECDICT 查询包入 Provider，建立通用结果映射、来源状态和策略入口；保持当前 API 行为兼容。
4. **接入第二词库**：以真实的第二数据源验证来源隔离、搜索、字段适配、去重、许可和页面布局，再决定是否引入统一索引。
5. **订阅与词典数据源选择**：定义计划权益、默认/fallback/aggregate 策略、缓存隔离及权限测试。
6. **多层查词服务**：拆分词典搜索、词形解析、容错查询和语境解释契约；保持精确查词路径低延迟且不依赖 LLM。
7. **多 LLM Provider**：在认证、隐私同意、限流、额度、评测和服务端密钥管理就绪后，实现 AI Router 与至少两个 Provider adapter；通过固定黄金样本比较质量、延迟、成本和稳定性。
8. **难度与练习 MVP**：明确难度依据后实现一个题型和基本答题记录；验证用户愿意持续使用，再拓展掌握度和复习算法。

## 11. 第一阶段验收标准

- 用户能够看到每个可用词库的名称、版本、条目规模和字段覆盖率，且统计口径清晰。
- 可以按词条搜索并分页浏览；请求不会进行无界全表扫描。
- 词条详情保留来源和版本；不同来源数据不会被误合并或丢失出处。
- 用户可以从词条详情收藏到个人学习中心；个人 note 不写回公共词库。
- 没有新增来源时，现有 ECDICT 查词和插件响应保持兼容。
- 页面、服务端和 API 均遵守来源许可和用户访问权限。
- AI 生成结果与词典原始内容分离并注明来源引用；Provider 故障或未授权时仍可使用词典查询。
- 用户触发 AI 功能前，能够理解上下文是否会发送给外部服务；额度、失败和 Provider 切换行为清楚可见。
- 暂不宣称具备权威难度等级；随机游戏在独立后续阶段实施。

## 12. 待决策问题

实施前需确认：

1. 词典浏览是否需要登录？词典目录和基础详情是否公开？
2. “覆盖情况”第一版是否只描述当前词库数据质量，还是要对标 CEFR、四六级、考研等外部词表？
3. 搜索默认只查 ECDICT，还是未来默认聚合用户已解锁的来源？
4. 付费模式是按词库解锁、按调用量/查询额度，还是按订阅等级？
5. 是否需要同时展示不同词库的多个释义，还是默认选择一个主来源、其余折叠？
6. 难度分档应基于词频、外部等级词表、人工标注，还是组合评分？
7. 接入第二词库前，需确认其数据许可、商用/缓存/展示/衍生数据限制。
8. AI 第一批任务是未命中补充、词义辨析、语境解释、短语/句子翻译，还是语义搜索？哪些任务需要用户主动触发？
9. Provider 选择应由产品全局默认、用户偏好、订阅权益还是按任务策略决定？是否允许并行比较多个模型？
10. 哪些上下文可以发送到第三方模型、保留多久、哪些 Provider 符合数据驻留/不训练要求？如何告知并获得同意？
11. AI 质量、延迟、单次成本和月度额度的验收阈值如何定义？谁能配置/查看 Provider 与模型版本？
